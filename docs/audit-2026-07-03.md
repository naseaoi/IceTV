## 结论速览

代码整体工程质量在同类自部署项目里偏上：SQL 全参数化、鉴权守卫统一、角色不信任 cookie、签名与口令比较均为恒定时间、代理与导入链路都有体量和内容类型防护。需要处理的问题集中在三块：

3. **登录态接口带 public CDN 缓存头**，在带缓存的部署形态下会跨用户泄漏。

## P1（优先修）

### P1-1 url-guard 被 IPv4 映射 IPv6 的十六进制写法绕过（SSRF） ✅

- **问题** `src/lib/url-guard.ts:299-305`（`normalizeIpAddress`）、`:284-297`（`isBlockedAddress`）：只对 `::ffff:` 后的**点分**写法做还原。对 `::ffff:7f00:1`（= 127.0.0.1）、`::ffff:a9fe:a9fe`（= 169.254.169.254）这类十六进制段写法，剥离前缀后剩 `7f00:1`，`net.isIP` 返回 0，被判为"非 IP → 不拦截"。已用 Node 实测：`net.isIP('::ffff:7f00:1')=6`，`net.isIP('7f00:1')=0`，`new URL` 保留该 host。
- **场景**：已登录用户（若开放注册则任意人）请求 `/api/proxy/segment?url=http://[::ffff:a9fe:a9fe]/latest/meta-data/...`，双栈主机上会连到云厂商元数据端点读取临时凭证；`::ffff:7f00:1` 打到本机回环服务。
- **修复**：识别所有内嵌 IPv4 的 IPv6（`::ffff:/96`、`::/96`、`2002::/16` 6to4），抽出末 32 位按 IPv4 规则判定；或直接拒绝任何内嵌 IPv4 的 IPv6 地址。补一条针对十六进制写法的单测。
- **修复后**：原状——十六进制映射地址畅通无阻直达内网/元数据；修复后——这类地址被还原为对应 IPv4 并命中内网黑名单，统一返回 `Blocked destination`。

### P1-2 配置读失败被当成"无配置"，回写默认值覆盖真实配置 ✅

- **问题** `src/lib/config.ts:344-372`：`db.getAdminConfig()` 抛错被 catch 后 `adminConfig` 为 null，走 `if (!adminConfig)` 分支执行 `getInitConfig('')` 并置 `shouldPersist=true`，随后 `saveAdminConfig` 把默认配置写回库。
- **场景**：MySQL 抖动 / 连接池超时导致一次读失败，紧接着写成功——源列表、用户角色、订阅被整体覆盖为默认值。`config_json` 损坏解析为 null 时同样静默重建。这是全项目唯一不可逆的数据丢失路径。
- **修复**：区分"读失败"与"确实无配置"。读异常时直接抛出或退回旧缓存，**绝不**在读失败后回写初始化配置；只有确证库中无记录才初始化。
- **修复后**：原状——一次瞬时读故障即可清空真实配置；修复后——读故障时保持旧配置或明确报错，配置不会被默认值覆盖。

### P1-3 登录态搜索/详情接口带 public CDN 缓存头，跨用户泄漏 ✅

- **问题** `src/app/api/search/route.ts:33-37,73-77,102-106`（`src/app/api/detail/route.ts` 同构，⚠️ detail 未逐行复核）：结果已按 `getAvailableApiSites(guardResult.username, config)` 逐用户过滤，响应头却是 `Cache-Control: public, s-maxage=...` + 仅按 query 变化的 `Netlify-Vary: query`。全项目无 `middleware.ts` 兜底覆盖这些头。
- **场景**：部署在 Vercel / Netlify / nginx 缓存后，源受限用户 A 先搜索，CDN 按 URL 缓存后把 A 的结果发给 B，或把全量结果发给受限用户；共享浏览器换账号同理。访问控制被 CDN 旁路。
- **修复**：登录态接口改 `private` 或 `no-store`；`public` 缓存只留给与用户无关的接口（如 douban）。若要保留边缘缓存，须按用户维度隔离缓存键。
- **修复后**：原状——受限结果经 CDN 跨用户可见；修复后——每用户结果只在自身会话内缓存，不再互串。

## P2

### P2-1 乐观锁是 check-then-act，且冲突错误从不暴露 ✅

- **问题** `src/lib/config.ts:599-636`：`assertConfigVersion`（一次读）与 `db.saveAdminConfig`（`INSERT OR REPLACE` / `ON DUPLICATE KEY`，无版本条件）之间存在 await 间隙，非原子。且 `ConfigConflictError` 没有任何 admin 写路由 `instanceof` 捕获，全部落 catch-all 返回 500。
- **场景**：两个管理员同时保存，双方都通过版本比对后先后落库，后写静默覆盖先写，且前端只看到 500 而非"请刷新后重试"。多实例共库时必然发生。
- **修复**：把版本列入库，用条件更新 `UPDATE ... WHERE version=?` 检查 `affectedRows` 实现真正 CAS；各写路由对 `ConfigConflictError` 返回 409 + 原始 message。
- **修复后**：原状——并发保存丢更新且报错误导性 500；修复后——冲突写被拒绝，前端收到 409 明确提示刷新重试。

### P2-2 校验后再 fetch 存在 DNS 重绑定 / TOCTOU 缺口 ✅

- **问题** `src/lib/url-guard.ts:89-141`：校验阶段自行 `dns.lookup`（带 30s 缓存）检查解析地址，`fetch`（undici）却独立再解析一次，两次结果可不同。
- **场景**：攻击者用低 TTL 域名，校验时返回公网 IP、fetch 时返回内网 IP / `169.254.169.254`，绕过即便修好的 IP 过滤（与 P1-1 叠加威胁更大）。
- **修复**：解析一次并"钉住"IP——用自定义 `dispatcher` / `lookup` 让 fetch 连到已校验地址，或校验通过后以固定 IP + 原 Host/SNI 发起请求。
- **修复后**：原状——校验的 IP 与实际连接的 IP 可能是两个；修复后——连接目标就是校验通过的那个 IP，重绑定失效。

### P2-3 登录限速可被 X-Forwarded-For 伪造绕过，且仅进程内内存 ✅

- **问题** `src/app/api/login/route.ts:52-66`：`getClientIp` 直接取 `x-forwarded-for` 最左值，key 为 `ip:username`；限速状态存于进程内 `Map`。
- **场景**：应用被直接暴露或代理未覆写该头时，暴力破解者每次请求带不同 `X-Forwarded-For` 即换新桶，`LOGIN_MAX_ATTEMPTS=10` 形同虚设；多实例部署时限速状态还不共享。
- **修复**：按可信代理跳数取真实连接 IP（或显式配置信任层数）；增加"按用户名全局"维度限速；多实例场景考虑共享存储。
- **修复后**：原状——换 IP 头即可无限尝试；修复后——限速绑定真实来源，爆破被有效遏制。

### P2-4 旧 owner 口令 HMAC 兼容期偏长、密钥熵低 ✅

- **问题** `src/lib/signing-secret.server.ts:51-64`，截止日 `:7`（`2026-10-01`，当前仍生效）：兼容期内用 `ICETV_PASSWORD`（常为低熵口令）作 HMAC 密钥验签，签名内容结构已知（`username:expiresAt`），且对所有用户会话开启。
- **场景**：拿到任一条 legacy cookie 即可离线爆破 owner 口令，成功后为任意用户名伪造会话。
- **修复**：缩短或立即结束兼容期，强制配置 `AUTH_SECRET`，不再用 owner 口令兜底验签。
- **修复后**：原状——一条旧 cookie 可离线撬开 owner 口令；修复后——验签只认高熵 `AUTH_SECRET`，离线爆破无从下手。

### P2-5 存储层 initPromise 失败后被永久缓存，瞬时故障即"变砖" ✅

- **问题** `src/lib/mysql.db.ts:106-112`（`src/lib/db.ts:26-33` 的 `storageInstancePromise` 同理）：`initPromise` 一旦 reject 不会重置，此后所有请求复用同一个 rejected promise，即使数据库已恢复仍持续失败到进程重启。
- **场景**：启动时 MySQL 短暂不可达。
- **修复**：初始化失败时把对应 promise 置回 null，允许下次重试。
- **修复后**：原状——启动期一次抖动让存储层整段瘫痪到重启；修复后——故障恢复后自动重连可用。

### P2-6 admin 新增采集源的 api URL 不校验、不 trim（管理员级 SSRF） ✅

- **问题** `src/app/api/admin/source/route.ts:58-79`：`add` 分支把 `api` 原样入库（`edit` 分支已 trim），后续 `searchFromApi` 的下游 fetch 不走 url-guard。
- **场景**：非 owner 的 admin 把 api 指向 `http://169.254.169.254/...` 等内网地址，搜索时服务端直接请求，形成管理员级 SSRF；含前后空格的 URL 也能入库。
- **修复**：`add` / `edit` 统一校验为 http(s) 且复用 url-guard 的内网黑名单，统一 trim。
- **修复后**：原状——admin 可让服务器打内网；修复后——非法/内网源在写入时即被拒。

### P2-7 giri 详情抓取无超时；下游响应体读取超时缺口 ✅ / ⚠️

- **问题** `src/lib/downstream-sources/giri.ts:47-60`：`fetchGiriHtml` 的 `fetch` 无 signal / 超时（文件已 import `createTimedAbortController` 却未用）。另 `src/lib/downstream.ts:141` 的 `abortState.cleanup()` 在 `response.json()/text()` 之前执行（⚠️ 未逐行复核），慢滴流响应可让 body 读取无限挂起。
- **场景**：girigirilove 慢源可把 `/api/detail` 挂住数分钟并占住连接（集数 × 源站放大）。
- **修复**：`fetchGiriHtml` 补 `createTimedAbortController`；`downstream.ts` 的 cleanup 统一移到 body 消费完成之后（`finally`）。
- **修复后**：原状——单个慢源拖垮详情接口；修复后——超时后快速失败释放连接。

### P2-8 两套存储大小写 / 长度语义不一致 ✅

- **问题** `src/lib/mysql.db.ts:114-148` 用 `utf8mb4_unicode_ci`（大小写不敏感）、`username VARCHAR(191)`；`src/lib/sqlite.db.ts:212-215` 是 `TEXT`（二进制敏感、无长度限制）。
- **场景**：MySQL 下 `ALICE` 能通过 `verifyUser`（\_ci 匹配 `alice`），但 cookie 里是 `ALICE`，`api-auth.ts` 严格 `===` 查不到用户 → 403；SQLite 下 `Alice`/`alice` 可共存两个账号。超长用户名 MySQL 报错 500、SQLite 全收。
- **修复**：入口统一 normalize（trim + 限长 + 字符白名单）；MySQL 关键列改 `utf8mb4_bin` 或应用层统一小写。
- **修复后**：原状——同名大小写在两种存储行为分叉、可致登录失败或重复账号；修复后——两端语义一致、账号唯一性稳定。

### P2-9 豆瓣图片代理存在两套真相源，设置显示与实际脱节 ✅

- **问题** `src/lib/utils.ts:11-30` 的 `getDoubanImageProxyConfig` 手写 key 直读 `localStorage`，值域含 `img3`、默认 `cmliussss-cdn-tencent`；而 `src/lib/douban-source.ts:8-38` 的 helper 值域**不含** `img3`、默认 `direct`。
- **场景**：设置面板选 `img3` 后图片按 img3 生效，但重开面板时 `readDoubanImageProxyType()` 把 `img3` 归一化为 `direct`，显示"直连"，显示与行为脱节。
- **修复**：`utils.ts` 改为消费 `readDoubanImageProxyType()` / `readDoubanImageProxyUrl()`；把图片代理值域独立出来（纳入 `img3`），与数据代理各自维护；统一默认值。
- **修复后**：原状——选了 img3 面板却显示直连；修复后——单一真相源，显示与生效一致。

### P2-10 "卸载保存" effect 实际每次渲染都触发 ✅

- **问题** `src/app/play/PlayPageClient.tsx:431-436`：卸载保存 effect 依赖 `[doSaveCheckpoint, doSaveCurrentProgress]`，而这两个函数在 `usePlayProgress` 里是普通闭包（无 `useCallback`），每次渲染都是新引用，导致 cleanup 在每次相关渲染后执行，而非只在卸载时。
- **场景**：播放页任何 state 变化（isPlaying、加载速度、源列表流式追加）都触发一轮 checkpoint 写入 + 进度保存；播放中 play_time 变化时会产生真实写库/请求。
- **修复**：`usePlayProgress` 内 `doSave`/`doCheckpoint` 用 `useCallback` 稳定化（内部已全走 ref，可安全空依赖），或卸载 effect 改空依赖 + 通过 ref 调最新函数。
- **修复后**：原状——播放中高频冗余保存；修复后——保存仅在真正卸载时发生。

### P2-11 测试套件偶发失败（sqlite 重复注册用例） ✅

- **问题** `src/lib/__tests__/sqlite-users.test.ts`：完整 `pnpm test` 首次运行时该用例失败（重复注册未抛错），单独跑、`--runInBand` 顺序跑、以及后续并行重跑均通过（复现率约 1/9，冷缓存并行下出现）。根因指向并行 worker 竞态叠加 `LocalSqliteStorage` 即便传 `:memory:` 也执行文件系统副作用（`mkdirSync`、WAL pragma、legacy JSON 迁移探测）。
- **场景**：CI 首次冷缓存并行执行时可能红，重跑转绿，掩盖真实回归信号。
- **修复**：`:memory:` 路径短路掉文件系统副作用与 legacy 迁移；或测试用独立临时目录 + 用后清理。
- **修复后**：原状——安全相关用例随机变红；修复后——测试确定性通过。

### P3-1 登录用户名枚举（封禁检查先于密码 + 时序差） ✅

## 已确认良好的部分

- **SSRF 主体防线扎实**：所有 proxy 路由统一汇入 url-guard（`skipInitialValidation` 由调用方预校验，安全）；重定向 `manual` 逐跳复检；IPv4/IPv6 内网段覆盖全面（含 CGNAT、link-local、ULA、NAT64、点分映射剥离）；`bangumi-cover` 目标 host 硬编码白名单。唯一缺口是 P1-1 的十六进制映射写法。
- **鉴权体系**：14 个 admin 路由全部走 `requireAdmin`/`requireOwner`；`userActions.ts` 有 owner-only 与"不可操作站长/自己"的细粒度校验；服务端从不信任 cookie 里的 role（从 DB 重算）。
- **密码学**：签名 HMAC-SHA256 用 `crypto.subtle.verify`（恒定时间）；owner 口令与 CRON_SECRET 用 `crypto.timingSafeEqual`；密码 bcrypt（原生优先、`bcryptjs` 回退）+ 惰性 rehash + `$2y$→$2b$` 兼容；备份 AES-256-GCM + scrypt。
- **SQL 全参数化**：mysql2 全 `?` 占位、sqlite 全预编译语句，含事务与批量导入路径，无拼接注入面。
- **导入链路**：条数/字节上限、`gunzip maxOutputLength` 防解压炸弹、类型/角色白名单，导入用户重置为随机口令（不信任上传哈希）。
- **缓存与资源**：server-cache（SWR + inflight 去重 + LRU 上限）、search-cache 容量上限与定时清理、login 限速表容量保护、bangumi-fetch 的 10MB 上限与 socket/timer 清理，均实现正确。
- **文档一致性**：`development.md` 列出的 27 个路径全部真实存在；通用弹窗（`ConfirmModal`/`AlertModal`）复用到位。
