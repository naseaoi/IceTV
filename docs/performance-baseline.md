# 性能基线

采集方法与固定场景，目的是让优化前后的数字可比。数字本身不入库，每次自行采集对比。

## 自动基线

运行：

```powershell
pnpm perf:baseline
```

该命令使用隔离的内存数据，不写入正式 SQLite 或 MySQL。固定场景包括：

- 10 万条播放会话的 7 段区间统计和 Top 统计
- 1500 次包含剧集与描述的搜索缓存写入
- 10 万次 VOD 分片容量预留

保存输出中的耗时、缓存条目数、估算字节数和淘汰次数。耗时只和同一机器、相同 Node 版本及相同电源模式下的历史结果比较。

## 上游并发回归

```powershell
node scripts/run-upstream-concurrency-check.js
pnpm test:mysql
```

第一条是隔离的合成服务层压测，不发送真实外部请求、不读取开发数据库。分别以 1、10、30、50 个并发客户端测冷/热两轮，覆盖首页三组推荐、详情、搜索第一页、VOD清单、调整封面缓存和分片接口。它调用真实业务加载器、共享缓存、SQLite预算与分片 GET；鉴权和上游响应被替换为固定数据流，图片编码、Next HTTP渲染与网络/CDN未纳入。

结果保存在不追踪的 `tmp/upstream-concurrency-report.json`，包含每个场景的本站调用QPS、状态码/失败率、返回字节/吞吐、每个上游的请求数/QPS/峰值活动流/失败率/字节数。这里的活动流是模拟连接，不是操作系统TCP连接。`cacheHitRate` 按被测缓存查询计数，`coalescedOrCachedRate` 是缓存与请求合并共同避免的回源比例；两者不能混为一谈。热分片仍需回源，因为没有本站分片内容缓存。

该压测断言缓存场景冷轮每个键只回源一次、热轮不回源，响应体最终无遗留活动流，分片峰值不超过主机连接上限。50人同时请求同一分片主机时，默认32连接预算会拒绝部分请求：这是上游保护触发，不代表50人可无损同时播放。若需容量验收，另在隔离部署中固定实际数据库延迟、源站码率、网关限速、实例数和用户行为做持续压测；不要将本机合成QPS当成生产吞吐承诺。

`pnpm test:mysql` 使用一次性MySQL容器，额外检查独立连接/存储实例的租约竞争、续租、过期接管和固定窗口原子性。未设置 `MYSQL_TEST_URL` 时普通Jest会跳过真实MySQL用例，所以不能只看 `pnpm test` 全绿。

## 浏览器端验证

使用生产构建，并固定 Chrome 版本、视口和网络设置。

| 场景              | 固定条件                            | 记录指标                                            |
| ----------------- | ----------------------------------- | --------------------------------------------------- |
| 冷 Service Worker | 清除站点数据后首次访问，Fast 4G     | 预缓存请求数、传输字节、安装耗时                    |
| 登录页            | 390 x 844、CPU 4 倍降速、录制 10 秒 | DOM 节点、长任务、脚本、渲染、GPU 内存              |
| 长时间 VOD        | 同一视频播放 30 分钟并拖动 10 次    | 分片请求、Cache Storage 操作、主线程长任务、掉帧    |
| 远程 MySQL        | 10 万条播放会话、固定网络区域       | `/api/playback-stats/summary` 的 p50、p95、查询次数 |

每次优化前后各执行 5 次，丢弃第一次预热结果，记录剩余 4 次的中位数。冷 Service Worker 场景不丢弃第一次。
