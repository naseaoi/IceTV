# 性能验证边界

只在性能相关改动时选择对应场景。测量数字不写入维护文档；同机、同 Node 版本和电源模式的结果才可直接比较。

## 自动验证

| 命令                                              | 范围                                                                                                                                                                                          | 不能证明什么                                                                                       |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `pnpm perf:baseline`                              | 内存数据上的播放统计、搜索缓存写入、VOD 分片容量预留                                                                                                                                          | 真实数据库延迟、HTTP 渲染或网络吞吐                                                                |
| `node scripts/run-upstream-concurrency-check.js`  | 1 / 10 / 30 / 50 客户端冷热轮；真实业务加载器、共享缓存、SQLite 预算与分片 GET，固定上游数据流                                                                                                | 鉴权、图片编码、Next 渲染、CDN、真实 TCP 容量                                                      |
| `node scripts/run-remote-mysql-overhead-check.js` | 一次性 MySQL 8.4、双向 TCP 延迟代理（`REMOTE_MYSQL_RTT_MS` 默认 20ms）、协议命令计数；VOD 单发/10 并发准入、普通/测速 detail、冷缓存持久化与 50 键播放记录；`REMOTE_MYSQL_SAMPLES` 默认 20 轮 | 生产容量、真实链路 RTT、签名验证、冷进程建表和每分钟维护首轮收益；p50/p95 只统计成功请求，失败单列 |
| `pnpm test:mysql`                                 | 一次性 MySQL 中的追更、共享缓存与资源租约一致性                                                                                                                                               | 生产 MySQL 的容量或整个存储接口正确性                                                              |

前两项不读取开发库、不发送真实外部请求。基线使用非空数据，覆盖 10 万条播放会话、1500 次带剧集和描述的搜索缓存写入、10 万次分片容量预留。

## 并发报告口径

输出为不追踪的 `tmp/upstream-concurrency-report.json`，包含本站和上游请求数、QPS、失败率、字节量、吞吐与峰值活动流。

- `cacheHitRate` 只按缓存查询计数；`coalescedOrCachedRate` 同时包含请求合并，不能互当缓存命中率。
- 活动流是模拟连接，不是系统 TCP 连接数；热分片仍回源，因为本站不缓存分片内容。
- 缓存场景要求冷轮每键只回源一次、热轮不回源，结束后无活动流；分片峰值不超过主机上限。
- 默认主机并发 32，50 客户端场景出现保护性拒绝不代表容量回归，也不证明 50 人可无损同时播放。
- 生产容量须在隔离部署中固定数据库延迟、码率、网关限制、实例数与用户行为持续压测，不能用本机合成 QPS 承诺。

真实 MySQL 与测试数据隔离要求见 [AGENTS.md](../AGENTS.md#测试)。

## 浏览器场景

使用生产构建，固定 Chrome、视口和网络。清站点数据的场景在独立浏览器上下文执行，避免清掉日常登录态。

| 场景              | 固定条件                       | 指标                                                                 |
| ----------------- | ------------------------------ | -------------------------------------------------------------------- |
| 冷 Service Worker | 清站点数据后首次访问，Fast 4G  | 预缓存请求、传输字节、安装耗时                                       |
| 登录页            | 390 × 844，CPU 4 倍降速，10 秒 | DOM、长任务、脚本、渲染、GPU 内存                                    |
| 长时间 VOD        | 同一视频 30 分钟并拖动 10 次   | 分片请求、Cache Storage、长任务、掉帧                                |
| 远程 MySQL        | 10 万条会话、固定网络区域      | 统计摘要 p50 / p95、查询次数                                         |
| 首播与换源        | 同一作品与源、有无详情快照各测 | 详情、历史恢复、清单发出、首片、`playing` 的先后与空档，在途请求峰值 |

优化前后各测 5 次，丢弃首轮预热后取中位数；冷 Service Worker 每轮保持冷态，不丢弃首轮。

首播与换源的时间点用导航时注入的脚本在 `document` 上捕获监听 `loadstart` / `loadedmetadata` / `canplay` / `playing`，结束后读 `performance.getEntriesByType('resource')` 对齐请求时序。注入脚本只对当次导航生效，刷新后须重新导航注入。开发构建只用于看先后顺序：StrictMode 会让 effect 请求成对出现，详情缓存也远短于生产。`DEV_PROXY` 只在非 production 进程生效，本地 `next start` 回源直连，源站失败会明显增多，失败样本不计入中位数。
