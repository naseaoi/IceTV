# 消息与追更边界

改消息中心、追更未读或关注动态前先读本文。实现见 `src/lib/tracking-sql.ts`、`src/lib/play-records.ts` 与 `src/components/messages/`。

## 数据与查询

- 未读状态从播放记录推导，不另存一份布尔值。查询按 `username` 走复合主键范围，不扫描其他用户记录；仅在单用户查询出现明确瓶颈时考虑派生列，并保证写入与迁移同步。
- SQLite / MySQL 共用 `tracking-sql.ts` 的谓词，只在数字、时间和布尔读取原语中区分方言；不要在两套存储里分别改未读条件。
- 播放记录分页的 `filter=updated` 与追更未读共用上述谓词，按保存时间和记录键倒序；消息列表继续按更新发现时间排序。两者匹配记录总数相同；消息通知设置关闭追更时，摘要的 `trackingUnreadCount` 置零，继续观看的更新数量仍取播放记录筛选总数。
- `filter=shelved` 复用播放记录分页与计数路径：保存时间严格早于 30 天前，且未到最后一集的 90% 进度；总时长未知的记录保留。分页和计数共用 `tracking-sql.ts` 谓词与同一截止时间，按保存时间和记录键倒序；分组刻度与更新筛选一致。
- `group_index` 与 `group_total` 同时有效时才使用组内刻度；已读基线必须与当前集数、总集数使用同一刻度。
- 旧分组标签可兼容，但**已推进的已读基线不批量回退到观看集数**：无法区分漏提醒与用户主动已读，回退会制造重复提醒。保留已有基线，只提醒后续新增集数。

## 追更默认值与元数据检查

- 播放记录的 `tracking_enabled` 显式设置优先；缺省时，`series_status = 'ended'` 默认关闭追更，`ongoing` 或未知状态默认开启。卡片、未读消息和两种数据库查询使用同一判定规则。
- 普通源优先识别备注中的完结词，其次连载词，再参考明确的完结标记、已更新集数达到正数总集数；只有一集且带电影类型或电影画质线索时也视为完结。单集本身不构成完结证据，giri / xgcartoon 等未提供状态的源保持未知。
- 播放保存和定时刷新同步作品状态，缺少新状态时保留记录已有状态，手动追更设置始终保留。旧记录在下次播放或详情刷新取得状态后应用默认值。
- 检查时间（`metadata_checked_at`）只由定时刷新写入，播放保存保留服务端已有值。客户端详情可能来自过期快照或搜索缓存，若保存时顶替检查时间，正在看的作品会一直推迟检查、漏掉新集。
- 更新发现时间（`update_detected_at`）由服务端按已有记录合并：同刻度总集数比已有记录多时写入本次保存时间，其余保存保留原值，不采信请求带来的值。它是消息排序与提醒水位的依据，随进度保存前移会让同一次更新反复提醒。
- 记录首次保存时，以同一用户最近一条标题与年份一致、刻度相同（同为整部，或同为等价分组）的其他源记录作为合并依据，沿用其基线、追更开关与发现时间。换源、播放失败自动换源和从搜索换源都走这里；各源更新快慢不同，否则新源已多出的集数会被当作已读。找不到可沿用记录时，基线取当前总集数。
- 刷新候选按优先级取：开启追更且未完结的记录（含已追平、等新集的）最先，看完的完结作品其次，关闭追更的最后；同优先级按检查时间从旧到新轮转。
- 检查时间写在条目处理时，晚于本轮开始时间。判断到期时参考时刻后移一个单轮时间预算（不超过检查间隔一半），否则调度周期等于检查间隔时，每条记录实际要隔两个周期才刷新一次。
- 详情获取失败的条目在本轮末尾按作品重试一次，仍失败或时间预算用尽时只写入检查时间与基线。
- 已完结且未显式开启追更的播放记录按 7 天间隔参与低频检查；普通检查间隔配置超过 7 天时沿用更长间隔。从未检查或检查时间异常的记录仍可立即入选。显式开启的完结记录、连载与未知记录沿用普通检查间隔（默认 6 小时）；候选仍受刷新预算和优先级约束。

## 关注动态

- 关注动态从公开评价和公开年度报告快照推导，评价首次公开时间（`first_published_at`）或报告首次公开时间严格晚于关注时间、个人已读水位和最近 30 天下界；单条已读按稳定消息标识排除。已读标识超过 200 条时，将最旧溢出项时间并入单调水位，并移除水位及之前的标识；该时间及之前尚未逐条阅读的动态也视为已读，同毫秒整体确认。全部已读推进水位，保留水位之后并发完成的单条已读。
- 年度公开消息 `follow-recap` 使用资料标识、年份和首次公开时间组成稳定 ID；刷新快照不再次提醒，取消公开或取消关注后自然退出。它与 `follow-review` 共用通知开关、已读水位和单条已读集合，计入关注动态未读数与摘要 revision；报告消息按发布时间、资料标识、年份在 SQL 分页，与其他消息使用来源前缀联合排序。
- 评价动态的稳定 ID、排序和游标都用首次公开时间，编辑、改分、私密再公开不产生新动态。`first_published_at` 由一次性迁移 `review_first_published_v1` 以原 `updated_at` 回填（含当时私密的评价），之后只在首次公开时写入；回填口径变了会把老评价当成新动态。
- 列表在 SQL 按首次公开时间、资料标识、作品归一化标题和年份分页；消息 ID 仍以原 JSON/base64url 编码，已读排除先在服务端解码为列元组。摘要只读取最新一条和独立 COUNT，revision 包含总数、分类计数及最新标识；列表条数与未读计数相互独立。
- 消息游标带版本：旧追更游标继续使用，旧关注动态游标因排序口径不同返回 400，重新打开消息列表取得新游标；消息 ID 与已读接口保持兼容。举报游标同样版本化，旧游标返回 400 并提示刷新列表。
- 未读公告按推送时间倒序固定在首屏最前；追更、收藏更新、关注动态、回复、新粉丝、评价点赞与管理通知按时间及来源标识联合排序，游标保留来源，时间相同也保持稳定分页。摘要的总未读数与 revision 同时包含这些动态。
- 关注动态使用不透明资料标识而非登录名；评价改为私密、被删除或取消关注后自然退出列表。

## 公告

- 公告分两类：站点须知是 `SiteConfig.Announcement`，修改不推送，游客在首页弹窗查看（按全文比对判断是否看过），登录用户在消息面板的公告视图查看；更新公告存在 `announcements` 表，`published_at` 为空表示草稿，只有推送才产生未读。
- 消息 ID 为 `announcement:<推送时间>:<行 ID>`。推送后修改正文不改 ID，不会再次提醒；撤回后重新推送会生成新 ID，重新形成未读。服务端读取单条公告时校验当前推送时间与 ID 一致，撤回或重新推送后旧 ID 的已读请求返回不存在。
- 未读窗口为最近 30 天，与社交通知一致。由于 `users` 表没有注册时间，新用户也只会看到窗口内的公告，不会收到全部历史。已读沿用单调水位加至多 200 条单条已读集合，全部已读把水位推进到请求时刻。
- 后台重复推送已推送的公告时保留原推送时间，不刷新也不再次打扰用户。

## 年度报告消息

- 开放期规则只在 `src/lib/annual-report-window.ts` 定义（12 月 20 日开放，至次年 2 月底），「我的」入口、消息与接口的未开放 403 共用它，改日期只改此处。
- 年度消息按用户时区在开放期推导，全年历史链接仍可访问；管理员预览不提前产生消息。资格按本地年度范围内正观看时长会话的起播时间判断，与报告中跨年桶的归属口径不同。
- 仅开放期且年度尚未读时执行一次按 `(username, started_at)` 范围索引的存在性查询；不为摘要轮询加载整年会话或批量写入通知。消息与公告一同置顶首屏，不参与动态游标，始终开启。
- 稳定 ID 为 `annual-report:<year>`，展示时间为该用户时区的开放日零点；已读按年度而非时间戳保存，切换时区不会让同一年度复活。全部已读只确认当前有资格收到的年度，避免尚无统计的用户提前消耗通知。

## 回复消息

- 回复收件人互斥：`reply_to` 为空（直接回复评价）只通知评价作者，回复某条回复只通知被回复者，始终排除发送者；他人在评价下互相回复不通知评价作者。两后端共用同一谓词，列表与 COUNT 同口径。通知从现存公开评价的回复推导，删除回复、删除评价或评价转私密后自然退出。
- 回复使用独立的已读水位与至多 200 条单条已读集合；溢出、同毫秒整体确认、全部已读保留水位之后并发已读的规则与关注动态相同。时间范围同为最近 30 天，摘要分别查询 COUNT 和最新一条。
- 回复消息 ID 包含创建时间与稳定回复 ID，联合分页排序使用 `review-reply:` 加回复 ID；不把编码后的时间字符串作为同毫秒排序键。评价类消息在消息面板内展示评价详情，详情中的“在播放页查看”跳转 `/play?title&year&tab=reviews` 并打开评价标签（窄屏打开评价面板）；新粉丝消息跳转对方主页；评价身份包含作者 `profileId`、`title_norm` 和精确年份，回复额外提供稳定 `replyId`。详情读取始终重新检查评价公开性。
- 后台举报游标使用 `reports-v3`，将评价与回复按类型、评价身份和回复 ID 一起排序；旧举报游标提示刷新。

## 新粉丝、点赞与通知设置

- 新粉丝从现存关注关系推导，收件人为被关注者，取消关注后自然消失；点赞按公开评价身份合并，计数包含最近 30 天窗口内全部他人点赞，先聚合再过滤已读，避免已读水位使计数变成增量人数。最新点赞时间相同时用点赞者用户名打破平局，公开载荷只返回其资料标识。
- 两类消息各自使用单调已读水位和至多 200 条单条已读集合，沿用关注动态的压缩与并发合并规则。点赞消息标识包含最新点赞时间，后续更晚的点赞重新形成未读；同毫秒点赞按同一通知确认。摘要 revision 同时包含合并点赞人数，取消部分点赞也能使摘要变化。
- `user_message_state.state_json` 持久化 `mutedKinds`；公告、年度报告与管理通知始终开启，追更开关同时控制收藏更新。列表、摘要、分类计数和 revision 在服务端跳过已关闭类型的查询。重新开启四类社交通知时，在状态写事务内比较最新设置并推进对应水位到请求时刻，关闭期间积累的消息视为已读；追更重新开启保留播放记录的原始基线。

## 收藏更新

- 源站点播收藏在没有同键播放记录时，定时元数据刷新发现总集数超过 `update_baseline_episodes` 即形成更新消息；未绑定的目录收藏、直播收藏不适用。目录收藏经[后台绑定](reviews-favorites.md#目录收藏)转成真实源收藏后，无需播放即可参与现有检测；定时任务只使用已有详情刷新结果，不增加绑定搜索或额外回源。
- 消息复用 `tracking-update` 类型、展示与“追更更新”开关，但 ID 与游标用独立前缀 `favorite-tracking:`，已读推进的是收藏基线而不是播放记录。同键播放记录存在（包括已关闭追更的）时由播放追更接管，否则会绕过播放记录的追更设置或重复提醒。
- 收藏自身的追更开关存于 `favorite_json.tracking_enabled`，缺省视为开启，只由 `PATCH /api/favorites` 原子写入；保存接口忽略客户端提交的值，重存、改观看状态、目录合并与绑定保留原值。关闭后消息、计数、已读语句与周历同时排除，重新开启不推进基线，与播放记录 `set-tracking` 一致。收藏卡片的开关在有同键播放记录时改写播放记录，否则改写收藏。
- 基线在新收藏时取当前集数；缺基线的旧收藏在首次刷新时以**刷新前**集数补写，用刷新后的集数会吞掉本次更新，用 0 会回灌通知。重存、改观看状态以及合并到已有真实源时保留原基线；目录转成新真实源时以绑定时的源集数重新起算，目录总集数不作为追更基线。绑定后的刷新保留目录标题与年份，持续关联原评价。已读只原子推进基线，旧消息只推进到该消息的集数，不覆盖并发刷新；MySQL 写 JSON 集数时显式转整数。客户端提交的基线与检测时间由服务端忽略。

## 追剧周历

- 候选在 SQL 内按当前用户的保存时间倒序取至多 200 条，包含已读作品。播放记录复用有效追更开关，且排除 `series_status = 'ended'`（即使显式追更开启）；收藏复用源站收藏范围，排除目录、直播、关闭追更的收藏和任何同键播放记录，收藏不判断完结。播放记录关闭追更时，同键收藏仍被排除。
- 有更新标记分别复用播放追更与收藏更新谓词。播放记录集刻度与 `getPlayRecordEpisodeDisplay()` 相同，收藏没有观看进度；最近发现更新时间原样保留，服务端不按 21 天窗口裁剪。
- 播出星期仅由 Bangumi 共享日历的中文名或原名与作品归一化标题、精确年份共同命中决定；空年份不命中，同名同年多个播出星期视为未知。日历回源失败保留作品列表。
- 星期推测由客户端按用户本地时区处理：近期发现更新的时间落在 21 天窗口内时给出推测星期，否则归入「近期无更新」。接口不把推测结果写入 `airWeekday`。

## 管理处理与账号通知

- 被删除的内容无法再推导通知，所以管理处理与账号变更写入 `user_notice_events`：类型为 `content-moderated`（删评价、删回复、标记剧透、删弹幕）、`report-result`（给举报人）、`account-change`（设 / 取消管理员、管理员改密、解封、实际可访问的源或直播权限变化）。事件必须与业务写入在同一事务内产生，`(recipient_username, event_key)` 唯一，重试与重复操作不重复通知。
- payload 只存作品、内容类型、数量等展示信息，不存密码、举报人、被删正文；消息不链接到已删除的内容。评价级联删除按收件人合并，弹幕按作品合并。权限通知比较的是用户实际可访问的源集合与直播权限（`src/lib/user-notice.ts`），等效配置变更不通知。
- 三类通知必收，不出现在通知设置里，共用 `user_message_state` 中一组独立的已读水位与 200 条已读集合，30 天窗口外的记录由定时任务清理；用户删除与 SQLite 用户名合并覆盖该表。
- 封禁账号以正确凭据登录时，登录接口返回 403 与 `code: USER_BANNED`，登录页明确展示；凭据错误时仍只返回通用错误，不暴露账号状态。

## 观后信

- `time-capsule` 从 `time_capsules` 中已送达且 `opened_at` 为空的本人信件推导，始终开启，不进入通知设置，不受 30 天窗口限制。单条已读与全部已读直接更新信件的 `opened_at`，重复打开保留首次打开时间；全部已读只覆盖请求开始时已送达的信件。
- 消息 ID 与同毫秒排序键均为 `time-capsule:<信件 UUID>`，展示时间与联合游标时间使用 `deliver_at`，写信时间另存 `writtenAt`。消息载荷包含信件 ID、作品、正文、送达时间及当时和当前评分，仅向本人返回。
- 未读数量及最新信件 ID 参与摘要和 revision；每次摘要只取最新未读信件与 COUNT，消息列表按送达时间、来源前缀与 ID 联合排序，不把全部信件加载到内存后分页。

## 摘要刷新

- `revision` 只用于判断是否需要刷新列表，不决定新消息提醒。提醒依据摘要的 `latestUnreadAt`（所有开启类型中最新未读事件的时间，点赞取最新点赞时间）与 `latestUnread`（该条的轻量预览，用作提醒文案）。客户端把已提醒到的时间按账号存在浏览器本地，单调推进、各标签页共享；只有它晚于该时间、页面可见且有焦点时才提醒，消息面板打开时只推进时间不弹出。已读消息、取消点赞、昵称变化不会触发提醒。
- 摘要请求带顺序保护，较早发出的迟到响应不覆盖已采用的结果。
- 摘要不增加短 TTL 服务端缓存；重复刷新由单标签页内的可见性节流和消息事件防抖合并，不提供多标签页请求去重。
- 删除失败时，列表可能已乐观移除，但不会派发 `messagesUpdated`；角标由下一轮可见页面轮询恢复，不要求同步回滚所有视图。
- 连续快速切换标签页时，补拉可能被最小间隔挡住；停止切换后恢复正常轮询，不为每个 focus 事件单独请求。

跨后端 SQL 与真实 MySQL 验证要求见 [数据与存储](data-storage.md#sqlite--mysql-双后端)。
