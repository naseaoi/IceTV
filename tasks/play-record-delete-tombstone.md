# 删除播放记录后迟到的保存会重建记录（待办，未排期）

## 问题

删除播放记录（继续观看移除、批量删除、清空历史）时，服务端同时清掉该记录的进度会话水位（`progress_session_id` / `progress_sequence`，见 [数据与存储](../docs/data-storage.md)）。删除之前发出、删除之后才到达的进度保存请求没有可比较的基线，会把记录重新写回，继续观看里被删掉的作品再次出现。

触发条件：

- 播放页关闭时的 keepalive 保存或网络重试，晚于另一个页面的删除请求到达。
- 另一台设备仍在播放该作品，继续保存（这种情况重建记录可视为正确行为，修复时需保留）。

相关代码：`src/app/api/playrecords/route.ts`（POST / DELETE）、`src/lib/play-record-write.ts`、`src/lib/sqlite.db.ts`、`src/lib/mysql.db.ts` 的删除与写入。

## 暂不处理的原因

迟到窗口通常只有毫秒级，删除又多发生在播放页关闭之后，实际触发概率很低。修复需要两侧存储都增加删除标记，成本明显高于收益。

## 可选方向

- 删除时保留墓碑：记录删除时的会话 ID 与服务端时间；同一会话、采样时间早于删除的保存直接忽略，新会话或删除后继续播放产生的保存照常写入。
- 墓碑需定期清理，SQLite 与 MySQL 同时实现并跑 `pnpm test:mysql`。

## 验收

- 删除后到达的、删除前采样的同会话保存不重建记录。
- 删除后用户继续播放或其他设备新会话的保存正常重建记录。
- 路由、存储契约测试与 MySQL 真实用例覆盖上述场景。
